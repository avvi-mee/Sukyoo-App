# Sukyoo — engineering audit, August 2026

Written 2026-08-17 against commit `c421931` plus uncommitted working-tree changes.

This audit exists because `LAUNCH_CHECKLIST.md` claimed *"Everything engineering-side is
built and verified … nothing here is blocked on more code"* and *"the local PGlite test
suite proves the SQL is correct."* Neither was true. **There is not one test assertion
anywhere in this repository**, and the SQL contained five critical, exploitable holes.

Grading here is deliberately unkind. "UI only" means the data is a `const` literal in the
file, regardless of how finished the screen looks.

---

## 1. Corrections to earlier assumptions

Five things that were widely believed about this codebase and are wrong.

| # | Claim | Reality |
|---|---|---|
| 1 | `react-native-notify-kit` is an unvetted substitute that can't do full-screen alerts and must be replaced with `@notifee/react-native` | It **is** Notifee — a maintained fork. Podspecs are still `RNNotifee.podspec`, the Java package is `io.invertase.notifee`, the copyright headers are Invertase's. Its API is a **superset** of upstream, it fully supports `fullScreenAction` + `AndroidCategory.CALL`, and it ships real iOS support including Notification Service Extension scaffolding in its Expo plugin. **Keep it.** Replacing it would be a downgrade. |
| 2 | iOS "is not configured at all" | Partially configured. Both apps already set `ios.bundleIdentifier` (`com.sukyoo.senior` / `com.sukyoo.family`) and `ios.supportsTablet`. Genuinely absent: `infoPlist`, `entitlements`, `UIBackgroundModes`, `buildNumber`, `GoogleService-Info.plist`. |
| 3 | There is no EAS config | `eas.json` exists in **both** apps with `development`/`preview`/`production` profiles. But every profile is **Android-only** (no `ios` key anywhere), `submit.production` is `{}`, and there is **no EAS project ID** in either app. |
| 4 | The 24 mockup screens need building | **All 24 already exist as files.** 8 are shells with const-literal data. |
| 5 | The notification library is what blocks iOS | The blocker is the **FCM payload shape**. `sos-trigger` and `calls-token` sent `{ token, data, android: {…} }` with no `apns` block — iOS silently drops a data-only push that lacks `apns-push-type: background` + `content-available: 1`. *(Fixed 2026-08-17.)* |

### And the finding that explains "the app looks broken"

**There was no seed data of any kind.** No `seed.sql`, no fixtures. `products`,
`product_categories`, `events`, `clubs`, `travel_trips`, `classes`, `content_items`,
`wellness_*`, `service_listings` and `doctor_profiles` all shipped empty, so most
"real data" screens were correctly rendering their empty state. Not a bug — an
absence that looked like one.

## 4. Security findings

All CRITICAL and HIGH items were fixed on 2026-08-17 in
`supabase/migrations/20260817120000_security_hardening.sql`,
`20260817121000_invite_hardening.sql`, and the Edge Function sources.

### Critical

1. **Self-service admin.** `handle_new_user()` took `role` straight from client-supplied
   `raw_user_meta_data`, and `signUpWithEmail()` exposes exactly that field. With signup
   open and email confirmation off, anyone could register as `admin` or `ops_agent` —
   and `create_order()` trusted `profiles.role` for authorization. `profiles_update_self`
   had no column restriction, so the same state was reachable after signup anyway.
2. **Forged family links.** `family_links_insert_participant` allowed inserting a row
   naming a **stranger** as `senior_id`; `family_links_update_participant` then let the
   attacker flip it to `active`. That yielded the victim's profile PII and their full SOS
   latitude/longitude history. Victim UUIDs were harvestable from
   `trip_bookings_select_own_or_seeking` and `doctor_profiles_select_all`.
   *The comment in `core_schema.sql` claiming "a family_link by itself grants NO record
   access" was true for health records and false for `profiles` and `sos_events`.*
3. **Fabricated health data.** Three INSERT policies checked the actor column instead of
   the owner column — `vitals_readings` checked `recorded_by`, `health_records` checked
   `uploaded_by`, `medications` permitted `prescribed_by` (and `FOR ALL`). Any user could
   write fake vitals into any senior's record, or inject an active medication that
   `ensure_todays_doses()` would materialize into the victim's daily reminder list.
4. **`sos-escalate` was unauthenticated.** Any caller could drive paid SMS and burn each
   event's single escalation attempt early, silently disarming the fallback.
5. **`calls-token` never validated `calleeId`.** Both apps declare
   `USE_FULL_SCREEN_INTENT` and render an incoming call over the lock screen, so this was
   a remote full-screen-wakeup primitive against arbitrary elderly users.

### High

6. **`razorpay-webhook` rejected every real delivery.** No `[functions.*]` block existed
   in `config.toml`, so `verify_jwt` defaulted true and Razorpay — which cannot present a
   Supabase JWT — got a 401 before the handler ran. **Payments were never captured.**
7. **Zero test assertions**, while two files claimed a PGlite suite verified the SQL.
8. **Zero table-level `GRANT`s** in any migration — only `grant execute on function`.
   Current Supabase cloud projects do not auto-expose new entities, so this risked blanket
   `permission denied for table` on every PostgREST call regardless of RLS.
9. **`doctor_profiles_update_self` let a doctor set their own `is_verified`** — the only
   gate on being bookable for telemedicine.
10. **`sos_events` had no UPDATE policy**, so `acked`/`resolved`/`cancelled` were
    unreachable from any client. Every event stayed "triggered" forever, the senior's
    screen never updated, and `sos-escalate` saw every past event as still open.
11. **`doctor_availability_slots` had no UPDATE policy**, so the client's
    `update({is_booked:true})` affected 0 rows **and returned no error** — unlimited
    silent double-booking.
12. **MSG91 SMS has never worked.** `sendSms` posted `{mobiles, message}` to the `/flow/`
    endpoint, which expects `template_id` + `recipients`. The SOS SMS fallback was inert.

### Medium (fixed)

13. Invite codes were plaintext 6 digits from non-cryptographic `random()`, 24h TTL, one
    namespace shared by all seniors, no rate limit, no attempt counter — the whole 10⁶
    space was brute-forceable.
14. `has_permission()` was **anon-callable** (Postgres grants EXECUTE to PUBLIC by
    default and the migration never revoked it) and takes `actor` as an argument — an
    unauthenticated oracle over the private consent graph.
15. `access_level` was never read anywhere. `create_order()` authorized a money-moving
    write via `has_permission(..., 'order')` while the UI only ever wrote `'view'` — so
    view-only consent authorized spending.
16. `permission_grants` had no uniqueness constraint, so toggling a permission on/off/on
    left duplicate live rows.
17. `orders_select_participant` omitted `payer_user_id`, so whoever paid couldn't see the
    order.

### Medium (open — flagged, not changed)

- `p_resource_id` on `has_permission()` is **dead code**: every caller passes `null`, and
  `pg.resource_id = NULL` is `NULL`, so a record-scoped grant can never match. It fails
  closed (safe direction), but per-record consent is fiction. Documented in the new
  unique index's comment.
- `permission_grants` has no `expires_at` — consent is perpetual until revoked.
- Revocation is **not retroactive for storage**: signed URLs already issued for
  `health-records` keep working past revocation, because the policy is evaluated only at
  signing time.
- `audit_log` is append-only by convention only — no `REVOKE UPDATE/DELETE`.
- `config.toml`: `minimum_password_length = 6`, no complexity requirements,
  `enable_confirmations = false` (unverified emails get live sessions), no captcha,
  `site_url` still `http://127.0.0.1:3000`. **Changing these alters the signup UX, so
  they are a product decision, not a silent fix.**
- `razorpay-order` has no `order.status` check and no idempotency key, so an already-paid
  order can be re-charged and `payments` accumulates a row per invocation.
- No rate limiting on `sos-trigger`.

### What only a paid external penetration test can tell you

This audit read the source. It cannot tell you: whether the **deployed** project's
configuration matches these migrations; whether storage RLS behaves as written against
real Supabase Storage (it is untestable locally — see `storage_buckets.sql:13`); whether
the mobile bundles leak anything at runtime; whether Agora's or Razorpay's own
infrastructure is correctly scoped to this account; or anything about network-level,
social, or supply-chain attack paths. **Budget for one before real users' health data is
on the platform.**

## 5. Dead code

**Exported hooks with no caller** (7): `useAddMedication`, `useHomeHealthcareBookings`,
`useAddEmergencyContact`, `useIncomingCall`, `useOrders`, `useWatchProgress`,
`useSaveWatchProgress`.

`useOrders` is notable — **there is no order-history UI in either app**, despite orders
being a core flow. The family app's "Orders" tab is a gift catalog.

**Unreachable feature:** `FontScaleContext` is consumed by `useFontScale()` in 17 files
and persists a scale key, but **`setScaleKey` is never called from anywhere**. The
accessibility font-size control — arguably the single most important affordance in an app
for elderly users — is fully built and has no UI to reach it. There is no settings screen
in the senior app at all.

**Dead UI:** family `HomeScreen` rows 2–3 (no `onPress`); senior Diagnostics "Book a lab
test" row (no `onPress`); `TripCompanionsScreen`'s `Switch` (no `value`).

## 6. Testing

Before 2026-08-17: **nothing**. No `*.test.*`, no `*.spec.*`, no `__tests__`, no
`supabase/tests/`, no jest, no vitest, no PGlite, no `deno test`, no CI, no `test` script
in any of the four `package.json` files, no lint config, no `typecheck` script.

The claims in `LAUNCH_CHECKLIST.md:34` and `storage_buckets.sql:13` that a PGlite harness
exists were fabricated. The policy bugs in §4 are exactly what one would expect from SQL
that has never been executed against a policy-enforcement test — finding #11 in particular
would fail the first such test anyone wrote.

### As of 2026-08-17 the suite exists

`supabase/tests/` — 24 assertions, run with `npm test`, gated in CI
(`.github/workflows/ci.yml`). `harness.mjs` boots a throwaway Postgres via PGlite (WASM,
no Docker — this repo is developed on Windows), shims the parts of Supabase's platform
schema the migrations assume (`auth.users`, `auth.uid()`, `storage.objects`,
`storage.foldername`, and the `anon`/`authenticated`/`service_role` roles), applies all
nine migrations, and then runs every assertion through a **non-superuser role with a JWT
claim set** — because a superuser bypasses RLS entirely and would make the whole suite
pass vacuously.

It covers the consent model end to end (unlinked → linked-ungranted → granted → revoked →
unlinked) plus a regression test for each critical finding above.

**It found two real bugs on its first two runs**, both of which would have reached
production:

1. `create or replace function` cannot change a function's return type — the invite
   migration would have failed outright when applied to the live database.
2. The invite rate limiter could never fire. It recorded a failed attempt and then
   `RAISE`d, which aborts the transaction and rolls back the very row it counts. Fixed by
   returning a status (`'ok' | 'invalid' | 'self' | 'rate_limited'`) instead of raising on
   expected user errors, with `accept_family_invite` now returning `jsonb`.
